## 难度路由

- 路径明确、可机械执行的命令与交付整理：`gpt-6-sol / high`。日志不明或跨服务问题转方案角色 `gpt-6-astra / high` 分析，修复代码仍交实现角色。
- 需求分析、普通跨文件定位：`gpt-6-astra / high`；简单任务由负责人直接拆分，不必唤醒方案角色。
- 高难架构、并发/迁移设计或长期未定位的问题：方案角色继续使用 `gpt-6-astra / high`，先缩小未知范围再交实现，避免重复全仓调查。
- 写业务代码和测试：固定 `gpt-6-astra / high`；代码审查固定 `gpt-6-sol / ultra`，复查只看修复差异。
- 模型切换由负责人在派单时明确指定，并在交接注明；不靠角色文本声称已经切换模型。

## 从需求到交付

1. **接单**：负责人把用户目标整理成一张短任务卡。需求清楚即推进，只把实质产品取舍和不可逆决策交用户确认。
2. **按需定位**：需要时交方案角色查相关模块，返回一个推荐方案、文件范围、关键风险；不为小改动写独立规格和计划文档。
3. **实现**：实现角色修改指定范围，并运行最近的行为测试及所属包类型检查。保留既有安全边界，避免内部重复校验和假想兜底。
4. **独立审查**：负责人暂停相关代码写入，交审查角色审本轮差异。报告确定的缺陷和具体依据；修复交原实现角色。派单回执或“收到/好的”不算执行完成，负责人须核对实际差异读取记录与审查结论；未执行的任务及时转派，不挂空等待。复查只覆盖变更及受影响路径，不固定多轮审查。
5. **技术交付**：集成交付角色复用实现者的实际检查结果；仅在代码变化、集成产生新影响、失败或证据缺失时补相关检查。不以全文档/全仓检查充当进展。
6. **用户检验**：每次阶段交付，负责人先说明本阶段可用功能，再给出可访问的页面入口、登录/账号准备、环境与数据条件、逐步操作、预期结果及已知问题。提供本地入口前确认对应服务已启动且 HTTP 可达；若未就绪先修复或明确阻塞，不让用户尝试一个尚未运行的地址。HTTP 可达仅说明服务就绪，交互、视觉及实际效果仍标记“待用户检验”。用户反馈后回到实现与受影响回归，再提供复验步骤。
7. **合并/发布**：按用户对具体 Git/部署动作的授权执行，沿用现有 CI。建立本团队本身不构成提交、推送、合并或上线授权。

纯文档和无行为变化的小任务可由负责人完成，不必经过全部角色。只有代码变更需要代码审查；不得把角色齐全变成每次都要走完的审批链。

完成当前 S4 后，负责人先复用本轮有效检查结果和已核对的隔离服务/环境事实，按下一步依赖整理一张短任务卡；最多安排两条按文件所有权划分的实现支线，差异稳定后进行一次独立审查。服务可用性必须通过实际连接、项目既有启动方式或其他可观测事实核对，不能仅凭 `Get-Command` 判断不可用。阶段报告分别列出已完成、未运行/阻塞和待用户验收，不提前提升任务状态。

## 共享工作区与通信

- 当前执行角色使用同一项目目录 `E:\Project\study-assistant-opening`。优先安排最多两条有独立交付价值的实现支线；负责人先划清文件所有权和依赖，同一文件及 Git 索引只允许一个写入者。不能独立拆分时保留单线，不为凑并发堆积未接入功能。方案、审查和检查可在范围稳定且互不干扰时并行。已稳定文件进入审查时，实现者可同时推进其分配范围内不冲突的下一片；负责人及时解除审查完成文件的写入限制，不串行等待交付汇总。
- 现有未提交内容属于用户。派单写明相关既有改动和本轮目标，不 reset、clean、覆盖、自动 stash 或宽泛暂存。审查范围限定到任务文件及本轮修改，不把整个脏工作区当本轮产物。
- 如确需两个实现任务同时写入，先安排互不冲突的文件所有权；只有用户要求隔离工作树时才为新角色选择 worktree，基于已明确的起点，不能假定未提交内容已同步。
- `packages/contracts`、公共导出、lockfile、CI、migration 编号按任务串行分配；多个检查进程不得同时清空同一测试数据库。
- 默认流水线为两条实现（gpt-6-astra / high）与稳定差异的独立审查（gpt-6-sol / ultra）交叠；定位与交付仅在有实际工作时参与。共享接口由一条支线负责，依赖方可先处理不依赖接口的部分；接口明确后再合流。单元/类型检查可按资源独立并行，复用同一隔离数据库的集成检查顺序执行。
- 用户已授权负责人向这些角色派单、追加修复任务并读取结果。角色完成后在自己的对话给出最终结果，负责人读取并统一回复用户；不需要用户复制粘贴对话内容。
- 功能实现角色可在已分配切片内使用多个实现子 Agent（gpt-6-astra / high），按互不重叠的文件和独立产出并行；主实现者先交接当前修改，再下放明确所有权，负责接口、公共导出、迁移编号和集成。子 Agent 可写对应测试，共用数据库的运行仍串行；实现自审不能替代独立的 gpt-6-sol / ultra 代码审查。不得重复已完成工作、为凑并发新增功能，或自行创建新的用户对话/扩展 backlog。角色不互相无限轮询；没有派单就结束当前轮次等待。
- 负责人仅在当前活跃轮次协调与读取状态；需要离开对话后持续监控时，另行明确安排，不假设存在常驻调度器。

## 任务卡与交接

派单直接放在对话里，复用既有任务编号（没有编号时使用简短名称），只保留这些信息：

```text
目标 / 用户可见结果：
范围 / 允许修改文件 / 相关既有改动：
约束 / 必须保留的行为：
建议的最近检查 / 已有结果：
返回内容：改动摘要、实际检查、未解决问题、用户检验步骤（涉及 UI 时）。
```

### 代码审查派单提示词

负责人每次填入具体任务，不发送只有角色说明或“请待命”的泛化派单。新对话首条消息也带实际待审任务；后续协调消息不等于新审查任务。

```text
现在执行只读代码审查，不要仅确认收到。
任务目标与当前修复：<明确行为/问题>
允许读取的文件与必要调用链：<具体范围>
已有检查结果、尚未完成项与当前写入者：<事实>

先用工具读取上述文件和本轮差异；未跟踪文件须直接读取。
只报告可触发的实质缺陷，不扩成风格重写或假想防御。
最终报告：结论；问题的文件:行号、触发、影响及最小修法。
无问题时：列实际读取的核心文件和核对路径，再说明未发现确定缺陷。
无法执行时：报告已尝试动作、具体阻塞和需要的信息。
不得以“好的/明白/收到”或“请再派单”结束本轮，未实际读取不得声称完成。
不改文件、不重复已有有效检查、不运行或委派浏览器验收。
修复复查只检查修复差异及受影响路径。
```

负责人从对话实际工具记录核对执行情况；出现空确认则转派或重建，不把空确认计入审查结果，不无限重复唤醒。模型参数明确设为 `gpt-6-sol / ultra`。
审查发现用“文件:行号、触发条件、实际影响、最小修法”表达。无实质问题直接说明；可选建议与必须修复的问题分开，禁止为证明工作量制造问题。负责人按实际影响决定哪些问题需本轮修复，未处理的真实风险必须明示。

状态只区分：待分派 → 实现中 → 审查/修复 → 待用户检验 → 用户已确认。无需实际使用检验的纯内部任务可记录“技术完成（不涉及用户检验）”。“检查通过”和“用户已确认”不得互相代替；待用户检验不阻塞无依赖任务继续开发。

正式产品范围与状态继续使用既有任务账本，不复制另一份 backlog；普通交接保留在角色对话中，不新增 hash、冻结 contract、baseline 或验收 evidence 文件。

## 非浏览器检查与实际使用检验

- Agent 可按改动执行单元/契约测试、隔离接口/数据库测试、类型检查、相关 lint，以及必要的构建。已经通过且内容未变的检查复用结果。
- 全量本地检查仅在明确请求时执行；合并/发布沿用现有 CI。纯文档修改只检查内容、链接和 diff。
- Agent 不运行或委派浏览器自动化、Playwright、截图、响应式、真机或真实场景验收；不将 HTTP 200、mock 成功当作实际可用。现有 CI 浏览器检查不改动。
- 失败按已有输出定位并最小修复，再重跑失败检查；无关历史失败记录但不扩成全项目停工。越权、数据丢失或当前功能依赖不可用仍须处理。
- 所有 shell 命令使用 `pwsh`，脚本首行 `$ErrorActionPreference = 'Stop'`，文件读写显式 UTF-8。以根目录及相关模块 `AGENTS.md` 为准。

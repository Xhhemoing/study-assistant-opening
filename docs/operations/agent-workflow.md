# 多工具并行开发与集成规则

本规则取代 [codex-team.md](../archive/operations/codex-team.md) 与 [project-lead-prompt.md](../archive/operations/project-lead-prompt.md) 中的旧角色、模型路由和派单流程；两者仅作历史。与根 `AGENTS.md` 共同约束执行，不因任务小或文档风险低豁免正式 PR 审查。最新明确授权优先，但本文不能覆盖平台或更高层仍有效的执行配额。

## 职责与车道

| 角色 | 职责与写权 |
|---|---|
| 主控 PM（Hermes） | 目标、依赖拆分、Kanban 调度、资源准入、验收与交接；不写业务代码，不计编码车道。不可把排队、started 或子任务 completed 当验交。 |
| 实现 worker（Pi 等已获准工具） | 独占原卡 allowlist，完成代码、最近验证、授权 Git 操作；优先原 owner／原会话续接，不重复实现。实际工具、模型与强度写入卡，不静默替换。 |
| 独立审查者 | 在稳定候选上只读核对实际 diff、调用链、失败路径和证据，指定 Claude Opus 5.5 high 为每 PR 正式审查；其他独立意见不能代签。 |
| 唯一集成者 | 执行集成分支与主线 Git 操作，独占共享接口决定、公共契约、依赖锁文件、schema／迁移编号和 STATUS；不与 worker 争写。该执行角色与 PM 调度角色区分。 |
| 用户 | 长期授权以外的高风险合并批准，含迁移的版本部署／生产配置／真数据／破坏迁移／定样审批，以及浏览器和真实使用验收。 |

目标容量是**八条隔离编码流，加评审／集成配套**，不是八个已经启动的 Agent，也不是允许突破运行配额。实际准入取决于以下条件全部满足：

1. 平台配额与本机资源允许；用户 2026-11-06 将同时运行的实现者上限定为 5，只读调查与审查不计。额度不足则只启动可容纳的就绪流，其余保留原卡依赖排队；不换会话或多开工具绕过。
2. 文件写集合互斥，接口已有一致决定，依赖产物可用；不能用不同目录掩盖同一个接口、迁移编号或共享状态冲突。
3. 工作区、数据库、Redis、端口、重验证槽和磁盘资源获准使用。注册旧 worktree 不等于活跃 writer；不为凑车道创建任务或工作树。
4. owner 明确且持有写权；切换前核原 owner 已停止写入并明确交回，不停止他人任务抢权。

项目不再采用固定 3 个 Agent／3 棵活跃 worktree 上限。worktree 按隔离需要复用或创建，但仍受上述实际配额及资源准入约束；它只隔离文件，不能隔离服务或重验证锁。清理工作树需确认无独有成果并取得清理授权，流程本身不授予删除权限。

| 角色 | Cursor 中的承担方式 |

| 只读调查 | `.cursor/agents/aistudy-explorer.md` 或内置 explore，不占实现名额。 |
| 每 PR 指定审查 | 指定的是模型 Claude Opus 5.5，渠道随工具：Cursor 中由 `.cursor/agents/aistudy-pr-reviewer.md` 执行，其他工具中用 claude CLI。 |
| 异家族审查 | Cursor 子 Agent 属 Claude 系列。按 2026-10-28 “Claude 写的交 GPT”原则，Cursor 中实现的代码与方案改动在指定审查之外，再由主会话以 `codex exec` 只读沙箱调用 GPT 审查；高风险 PR 一律需要。 |
| 任务卡与交回 | 任务卡随派单 brief 完整下发，结果以 PR 正文为持久记录，会话内用 TodoWrite 跟踪；Hermes Kanban 可用时仍以原卡为准。 |

子 Agent 默认共享主会话的 checkout，会互相覆盖改动，所以写文件的子 Agent 必须使用独立 worktree，同一 checkout 内只运行只读调查和审查。需要本地验证的 worktree 单独 `npm ci`，不软链共享 `node_modules`，否则 workspace 包会解析到其他 checkout 的源码。本机没有 PostgreSQL/Redis 时，数据库集成、handler、浏览器和 build 交精确 head CI。

审查者同样运行在共享 checkout 中，所以在 Cursor 里，下文“指定审查使用该提交的独立干净快照”由精确 head 的 git 对象承担：差分、文件、搜索和调用链都从 head 对象读取，不以工作区内容为证据；确需完整工作区时由主控为该 SHA 建 detached worktree。结束时的核对相应改为确认 PR head 未变。派单操作见 `.cursor/rules/parallel-dispatch.mdc`。

## 持久 Kanban 与原 owner 续接

所有可独立交付的执行工作使用持久 Kanban，`workspace=worktree`。父子依赖用 `parents` 表达，不以聊天记忆或重复卡代替。原卡未完时优先续原 owner、原会话、原候选；新卡只能对应不同结果，不因模型超时、交回或状态询问复制同一业务任务。派单前确认实际无在途 writer／验证，投递回执仅证明投递。

任务状态与事实分开：
- `ready`／排队不是开工，实际接受须 comment 原卡、执行身份、工作区和写集合。
- 实施过程中记录真实源码、命令和终态；工具超时、锁拒绝、缺退出码不是通过。owner 失联先核进程与产物，不按 pane busy 或过期心跳猜完成。
- 阻塞注明原因、责任环节、已做恢复、保留候选和下一检查点；仅依赖该阻塞的流暂停，其他就绪独立工作继续。
- 提交／推送／PR 不等于正式验交。指定审查或用户批准未齐保留 `needs_input`，不能为写 metadata 把卡虚标 complete。
- 完成与交回附真实 diff、命令退出码、完整提交和远端 SHA、PR、未验项及当前写权。CLI 若仅允许对 done 卡编辑 metadata，使用原卡结构化 JSON metadata 评论，不直接改数据库或伪造 done。

### 必填任务卡

```text
目标：<独立可验的用户结果；本卡具体完成线>
owner／执行身份：<唯一 writer、原生会话；PM 与集成执行者>
workspace：worktree；工作区／分支：<核实可用的位置>
允许路径：<精确文件／目录；只读审查填无>
只读要求：<是否只读；审查须绑定精确稳定 head 的独立快照，结束核未改>
红线：真实产品测试模型按当前授权仅用开发网关 GPT；独立已授权 Opus 审查不受此产品测试路由限制；不本地浏览器、不碰生产／真数据／未授权费用
parents：<前置卡 ID，无则明确无；对应就绪证据>
接口决定：<输入／输出、owner、安全／失败语义；变更回集成者>
共享独占项：<契约／锁文件／迁移编号／STATUS；不得自行写>
限定验证：<最近 unit 文件、所属包 types、必要集成与执行者；文档仅 diff>
风险：<低／高及依据；迁移与回退、权限／费用／取消影响>
Git 授权：<commit／push／PR base／是否可合；部署单独审批>
预算：实现 1 次＋指定 Opus 审查 1 次＋必要集中修复 1 次
metadata：changed_files、commands＋真实 exit、results、commit、remoteSHA、PR、unverified、owner／是否交回
```

任务卡不能授权突破更高层限制。共享接口未定先解决依赖，禁止各流分别写出不兼容契约。开发成本原则上不约束执行，不为压缩成本牺牲结果；但不改变产品费用策略、付费模型调用授权、预算规则、有效配额和运行资源限制，不购买额度绕过审查阻塞。

## 连续实施与验证准入

实现者在 allowlist 内连续完成一个可用结果，不为每个内部函数另建卡、PR 或评审。只加载当前所需文件与技能；恢复时核原卡、工作区、最新差异和直接缺验，不反复读长 STATUS／总计划。STATUS 由唯一集成者按实际交付更新，普通 worker 只读必要行。

- 实际隔离的文件与运行资源可并行编码／验证；共享环境重验证必须经现有 `run-heavy` 串行，不能只靠“不同 worktree”并跑数据库、类型或构建。不得停止或抢占其他任务。
- 轻量源码、语法、diff 与现成近邻检查先行；只跑本片直接相关 unit／包 types／集成，不先全套再定点。纯文档只审实际 diff 和规则一致性，不跑业务测试或服务。
- 本地资源不足时先限制新卡／工作树／重验证准入，不以本地全套、构建或大包 PG 阻塞已授权实施。完整类型、构建和测试门禁交现有远端 CI；未运行范围如实记 `unverified`，不能把定点 roots 绿说成包／依赖闭包绿。
- 已有验证在源码版本、输入、环境与覆盖仍有效时复用。新改动只补直接缺验；集成的新影响补相关检查，不把不相干局部绿相加成整体绿。
- 失败按 failure → cause → fix → recheck：保留红测、锁拒绝、超时与缺终态，足够诊断后只做最小修复，不盲重试或降低断言／安全 guard。真正隔离 worker 的并行仍须获准且服从当前配额。
- 实现 1 次、指定审查 1 次、必要集中修复 1 次后若仍受阻，返回最小阻塞和下一决策，不滚动加派、重复全审或新建通用评测／Agent 框架。

## 每 PR 正式审查与分支规则

所有 PR（含低风险文档、测试和集成提升）须 **Claude Opus 5.5 high 批准＋精确最新 head 的 required CI**，实现者自查不能代替。只读独立核验可以补证，但不能代 Opus。高风险另须指定异家族审查及用户明确批准；不得自行降模型、拿空 verdict／工具错误／旧 head 批准放行。指定渠道受阻只阻对应集成门禁，不冻结无依赖的独立实施／近验。

| 风险与路径 | 目标与准入 |
|---|---|
| 低风险：不改变授权、隐私、事务、迁移、数据正确性或相关安全语义 | 功能分支 PR 到 `integration/opening`；指定 Opus 批准与该 PR 精确 head required CI 全过后，由唯一集成者按授权集成。文档／小改动也不免审。 |
| 集成提升 | 唯一集成者整理 `integration/opening` 的已达标结果，以完整相对 base 差分向正式主线 `feat/opening-release` 提升；提升 PR 同样满足指定 Opus 与精确 head required CI，达门禁即串行进入主线，不再固定每天两次批次。 |
| 高风险：授权、隐私、事务／并发、迁移、数据正确性，或影响这些边界的取消／生命周期／费用行为 | 从安全基线独立 PR 到 `feat/opening-release`，不借低风险集成池带入；完成指定 Opus、异家族审查与精确 head required CI 后，仍以 `needs_input` 等用户明确批准，不能由 Agent 自动合并；满足下节“用户长期授权”全部条件的，视为已获用户明确批准。 |

### 用户长期授权

用户于 2026-11-05 明确给出以下长期授权，2026-11-06 扩展第 1 条并新增第 3 条，有效至用户撤回。授权只由唯一集成者执行，不扩展到其他角色。

1. **高风险 PR 合入 `feat/opening-release`**：在上表高风险门禁（指定 Opus、异家族审查、精确 head required CI、独立主线 PR）全部完成的前提下，同时满足以下条件时，视为已获用户明确批准，由唯一集成者按 expected SHA 以 merge commit 合入。用户 2026-11-06 决定两个模型都批准就合并，含迁移的 PR 也适用。
   - 指定 Claude Opus 5.5 high 与 GPT 异家族审查都对当前 head，或对相对 base 的完整 `--binary --full-index` 补丁 SHA-256 与当前 head 相同的已审版本，给出 approved，且没有未关闭的 blocking。
   - 当前精确 head 的 required CI 全部通过。
   - 合入内容与已审补丁逐字节一致。存在文件重叠的三方合并时补丁不再逐字节一致，本授权不适用：须对合并结果重新取得两个模型的审查，或由用户逐次批准。
   - 合入不等于执行：含迁移的 PR 合入后，包含该迁移的版本部署仍须用户逐次批准（见本节末）。生产配置不在仓库内，不属于本条。
   - 每次合入都在 PR 正文记录所依据的审查、CI 和等价证明。
2. **清理**：已完全合入主线、相对主线没有独有提交、工作区干净的 worktree 和远端分支，可由唯一集成者回收。有独有提交、未合并、属于线上参照树或无法判断的，仍须用户决定。
3. **不含迁移的主线版本部署**（2026-11-06）：同时满足以下条件时，由唯一集成者用目标版本自带的受管发布脚本部署主线精确 head，不再逐次等用户批准。
   - 目标版本与线上版本之间迁移目录没有差异。
   - 目标版本中的每个 PR 都经指定 Claude Opus 5.5 high 与 GPT 异家族审查；只经指定审查合入 integration 的低风险 PR，由提升 PR 的 GPT 审查覆盖。
   - 目标 SHA 的 required CI 全部通过。
   - 部署前在会话中向用户给出精确提交号、迁移差异与回滚方案；部署后只读核验健康检查返回的提交与服务状态，结论按“公开仓库信息边界”记入 STATUS。

以下事项不在授权范围内，仍须用户逐次审批：含迁移的版本部署、迁移执行、生产配置、真实数据操作（含导出、改写）、破坏性迁移、定样。

接口或用途使风险升级时先回 PM／集成者调整原卡和依赖，不以文件少、测试过或分支名认定低风险。PR 写明全部相对 base 改动及未验范围；不能只描述最后一笔修复，也不能以旧候选已批准覆盖新 head。若合并目标变化或集成修改影响审查覆盖，重新确认实际差分和对应门禁，不静默沿用旧批准。

Git 使用 Conventional Commit，正式仓库为 `Xhhemoing/study-assistant-opening`，remote 命名为 `study-assistant-opening`（新克隆把 `origin` 改为此名），不推任何旧仓库 remote；commit、push、PR、合并及发布各自服从当前授权，禁止 force、reset／clean／覆盖他人成果。没有迁移的卡明确写无，不捏造回滚。允许的本地完成与代码交回不是已交付用户；最终合并和用户效果另记真实证据。

含迁移的版本部署、生产配置、真数据导出／改写、破坏性迁移、定样仍需用户审批；不含迁移的主线版本只按“用户长期授权”第 3 条部署。开发成本原则不解除产品费用策略或该审批边界。不得用“加快交付”推导发布授权。

## 浏览器、信息与按需工具边界

Agent 不自行或委派本地浏览器、Playwright、截图、真机验收；用户浏览器验收与 CI 浏览器分别报告。保持现有 CI 浏览器检查，不关闭或降门禁；待用户验收不冒称已过，也不阻塞独立后继开发。

工具按实际可用能力分工，不把历史“某工具不可用”或某次服务恢复当永久事实。模型与网关配置、密钥只留私有授权环境，不复制到仓库；公开文档不写主机地址、绝对运行路径、PID、生产拓扑或运维快照。只读审查不写业务，换执行者须明确 owner 交接，不把新会话当配额逃逸。

### 工具执行与只读审查

- 真实产品测试模型按当前授权仅使用开发网关 GPT 系列，不自行调用其他付费 API 或增加未授权费用。独立、已获授权的指定 Opus 审查属于审查门禁，不受产品测试路由限制；它仍须遵守当前渠道、模型、强度、配额和只读授权，不据此授予产品调用权限。
- 单次 CLI 审查运行不假设已加载 `AGENTS.md`。派单 brief 必须写全目标、允许路径／只读要求、生产与真数据禁区、本地浏览器禁令、模型／费用授权和 Git 操作边界；不得仅给文档链接代替红线。
- 指定审查绑定精确、稳定的 PR head，使用该提交的独立干净快照；送审期间不改候选。审查开始记录完整 SHA 与干净状态，结束核对 SHA 未变、检出及暂存区未被修改（包括非预期新增文件）；有变化先报告，不能把它当作原候选的只读批准。其他互斥工作可继续，但不共享该审查快照写权。
- 工具只按当前获准且实际可用的能力运行，不恢复历史工具名单或旧路由。模型与网关配置、密钥保留在仓库外私有授权位置，凭据仅经获准环境或秘密存储注入，不写入 brief、公开日志或仓库。

### 图谱按需维护

图谱用于定位和导航，不作为日常完成门禁。源码变化后，若已有 `graphify-out/graph.json`，沿根 `AGENTS.md` 规则设置 `graphify-out/needs_update`；纯文档／注释改动不刷新。查询前检查陈旧标记；stale 图只作历史导航，当前调用链、依赖和影响范围必须回读现行源码，不借用其他版本的图冒充当前关系。

只有当前授权涵盖且确有刷新需要时，才在对应有效工作区运行一次 `graphify update .`，等待终态并记录失败／未完成；用户明确要求刷新同样服从写权与资源准入。不得按每个任务、提交、状态回复或批次自动刷新，也不静默启动后台更新，完成前不把旧图说成新图。

已有结构图仅需重算社区／图分析时，可按授权运行 `graphify cluster-only . --no-label`（不调用模型）：它只更新 graph／report 及可生成的 HTML，不更新 wiki 或 manifest；其他导出须按需单独生成核对。刷新期间禁止并发 Graphify 写入；禁止用 `--force` 绕过缩减保护，也不得以跳过关系清理的原始 `--no-cluster` 输出代替正式图。图谱位于忽略的 `graphify-out/`，不提交到仓库。

图谱不减少源码、适用检查、独立审查及 CI 的要求。纯文档不新建 evidence／baseline／费用账本或状态平台；持久任务事实在原 Kanban，项目交付摘要由唯一集成者写 STATUS，worker 收工在原卡交回结果与未验项，二者不互相伪造完成。

# 多工具并行开发与集成规则

本规则取代 [codex-team.md](../archive/operations/codex-team.md) 与 [project-lead-prompt.md](../archive/operations/project-lead-prompt.md) 中的旧角色、模型路由和派单流程；两者仅作历史。与根 `AGENTS.md` 共同约束执行，不因任务小或文档风险低豁免正式 PR 审查。最新明确授权优先，但本文不能覆盖平台或更高层仍有效的执行配额。

## 职责与车道

| 角色 | 职责与写权 |
|---|---|
| 主控 PM（Hermes） | 目标、依赖拆分、Kanban 调度、资源准入、验收与交接；不写业务代码，不计编码车道。不可把排队、started 或子任务 completed 当验交。 |
| 实现 worker（Pi 等已获准工具） | 独占原卡 allowlist，完成代码、最近验证、授权 Git 操作；优先原 owner／原会话续接，不重复实现。实际工具、模型与强度写入卡，不静默替换。 |
| 独立审查者 | 在稳定候选上只读核对实际 diff、调用链、失败路径和证据；正式模型为指定 Claude Opus 5.5 high 与独立 GPT，按下文 v2 风险门禁决定合入前审查或 L 后补审，其他意见不能代签。 |
| 唯一集成者 | 唯一合入 `integration/opening` 和 `feat/opening-release`，独占共享接口确认、公共契约、依赖锁文件、schema／迁移编号和 STATUS；不与 worker 争写。开 PR、派单或接管都不产生第二合并权；该执行角色与 PM 调度角色区分，不限定所在工具。 |
| 用户 | 长期授权以外的高风险合并批准，含迁移的版本部署／生产配置／真数据／破坏迁移／定样审批，以及浏览器和真实使用验收。 |

目标容量是**八条隔离编码流，加评审／集成配套**，不是八个已经启动的 Agent，也不是允许突破运行配额。实际准入取决于以下条件全部满足：

1. v2 运行中实现者最多 5 个，只读调查与审查不计，待审 PR 不占实现名额；L 不占 H 积压容量但仍计 writer。每次新增前 available 至少 500 MiB，否则停止新增，不停止已有获准轻量实施。未合入 H 栈最多 2 层；未合入 H PR 超过 4 个时暂停新 H，优先 L 或修复。平台配额与实际资源仍须满足，不换会话或多开工具绕过。
2. 文件写集合互斥，接口已有一致决定，依赖产物可用；不能用不同目录掩盖同一个接口、迁移编号或共享状态冲突。
3. 工作区、数据库、Redis、端口、重验证槽和磁盘资源获准使用。注册旧 worktree 不等于活跃 writer；不为凑车道创建任务或工作树。
4. owner 明确且持有写权；切换前核原 owner 已停止写入并明确交回，由 PM 协调续接原卡、原候选和原成果，不停止他人任务抢权。错误码、沉默或无新推送不是自动接管授权；接管者不因此取得 integration 或主线合并权。

项目不再采用固定 3 个 Agent／3 棵活跃 worktree 上限。worktree 按隔离需要复用或创建，但仍受上述实际配额及资源准入约束；它只隔离文件，不能隔离服务或重验证锁。清理工作树需确认无独有成果并取得清理授权，流程本身不授予删除权限。

## 工具隔离与当前执行约束

当前授权 runtime 为 full-access，仍须遵守卡片 allowlist 与 Git／生产权限；runtime 不等于合并或部署授权。T3 实现子树由平台 `isolation: "worktree"` 准备，worker 不用 shell 建树，不写父 checkout；不为低风险卡复制依赖。Cursor 的 shell 建树和子 Agent 约定仅适用于下一节，不推广到 T3。

v2 审查流水线独立限流：稳定候选交回后安排独立 GPT，最多 3 个并发；Opus 在 available 至少 1.2 GiB 时最多 2 个，否则最多 1 个，且须满足实际资源。优先 H 合入前审查、L 补审缺陷复查、L 补审。渠道不可用如实记未审，不用自审、空结论或未经授权换模型代替，不购买额度或反复探测绕过阻塞。

## Cursor 中的执行映射

以下仅为 Cursor 专属操作映射，不是新的合并授权。按用户 2026-11-08 的 2A 决定，规划、派单与审查、集成可分工，但 integration 与主线均只有唯一集成者合入。

| 角色 | Cursor 中的承担方式 |
|---|---|
| 规划会话（主控 PM 的规划部分） | 只读调查、拆卡、核接口，把完整任务卡写进仓库外的卡片目录 `ready/`；公共接口起草后交集成者确认。计划范围内产品细则由 PM 按既定规则设默认值；必须由用户决定的问题集中提出，每 12 小时最多一次。不派单、不实现；除非出现具体故障，不开流程类 PR。 |
| 派单与审查会话（主控 PM 的调度部分） | 从 `ready/` 取已满足依赖、接口确认和写集合／资源条件的卡并移到 `active/`，建 Cursor worktree、派实现者，对 PR 发起对应审查；候选交唯一集成者，不自行合入 integration。也可起草卡，接口确认标准相同；完成状态须按实际合入和交付事实记录。 |
| 集成会话（唯一集成者） | 唯一合入 `integration/opening` 和 `feat/opening-release`：L、提升与 H 均按下文 v2 门禁。独占 STATUS、共享接口确认、公共契约、依赖锁文件、schema／迁移编号，按实际 PR 事实批量同步总计划附录 F，不重做已交卡。不含迁移的主线版本仍须满足既有部署授权；含迁移的版本部署、迁移执行、生产配置、真实数据操作、破坏性迁移和定样仍逐次审批。 |
| 实现 worker | 派单与审查会话先用 `git worktree add` 建好独立 worktree 与卡片分支，再派发遵循 `.cursor/agents/aistudy-lane-worker.md` 的子 Agent 在其中实现；同时运行不超过 5 个。`best-of-n-runner` 在本机 IDE 中不提供隔离，不用于实现。迁移、事务、跨包卡仍按 2026-10-28 决策表交 Codex CLI（gpt-6.1-terra xhigh）实现，改由 Cursor 子 Agent 承接须用户决定。跨包卡指改变任一 `packages/*` 中被其他包消费的公开契约、类型或函数签名的卡（例如 `packages/contracts` 的 schema 与工具定义，或 domain/database 被应用消费的导出），由写卡会话起草、集成者确认后在卡里界定并写明实现者。 |
| 只读调查 | `.cursor/agents/aistudy-explorer.md` 或内置 explore，不占实现名额。 |
| 指定 Opus 审查 | 模型为 Claude Opus 5.5 high；H 合入前通过，L 合入后补审。Cursor 中由 `.cursor/agents/aistudy-pr-reviewer.md` 执行（类型不可用时，获准的 `generalPurpose` 按同一说明执行并注明，模型要求不变）；其他工具只用当前获准渠道，不以工具名替代模型批准。 |
| 独立 GPT 审查 | L 与 H 合入前须独立 GPT 批准，提升须 GPT 快审；实现者自审不能代替。Cursor 使用获准 `codex exec` 只读沙箱，其他工具按实际可用且获准渠道，不把某次环境快照写成永久路由。 |
| 任务卡与交回 | 任务卡放在仓库外的卡片目录，按 `ready/`、`active/`、`done/` 三个子目录流转，派单时完整写进 brief；结果以 PR 正文为持久记录，会话内用 TodoWrite 跟踪；Hermes Kanban 可用时仍以原卡为准。 |

Cursor 子 Agent 默认共享主会话的 checkout，会互相覆盖改动，所以写文件的子 Agent 必须使用独立 worktree，同一 checkout 内只运行只读调查和审查。仅在卡片需要本地验证且资源获准时，才在对应 worktree 单独 `npm ci`，不软链共享 `node_modules`；纯文档不安装依赖。本地依赖服务不具备时，相关集成／handler 与完整 build 交精确 head CI，本地浏览器始终由用户负责。

审查者同样运行在共享 checkout 中，所以在 Cursor 里，下文“指定审查使用该提交的独立干净快照”由精确 head 的 git 对象承担：差分、文件、搜索和调用链都从 head 对象读取，不以工作区内容为证据；确需完整工作区时由发起审查的会话为该 SHA 建 detached worktree。结束时的核对相应改为确认 PR head 未变。派单操作见 `.cursor/rules/parallel-dispatch.mdc`。

## 持久 Kanban 与原 owner 续接

所有可独立交付的执行工作使用持久 Kanban，`workspace=worktree`。父子依赖用 `parents` 表达，不以聊天记忆或重复卡代替。原卡未完时优先续原 owner、原会话、原候选；新卡只能对应不同结果，不因模型超时、交回或状态询问复制同一业务任务。派单前确认实际无在途 writer／验证，投递回执仅证明投递。

任务状态与事实分开：
- `ready`／排队不是开工，实际接受须 comment 原卡、执行身份、工作区和写集合。
- 实施过程中记录真实源码、命令和终态；工具超时、锁拒绝、缺退出码不是通过。owner 失联先核进程与产物，不按 pane busy 或过期心跳猜完成。
- 阻塞注明原因、责任环节、已做恢复、保留候选和下一检查点；仅依赖该阻塞的流暂停，其他就绪独立工作继续。
- 提交／推送／PR 不等于正式验交。指定审查或用户批准未齐保留 `needs_input`，不能为写 metadata 把卡虚标 complete。
- 完成与交回附真实 diff、命令退出码、完整提交和远端 SHA、PR、未验项及当前写权。CLI 若仅允许对 done 卡编辑 metadata，使用原卡结构化 JSON metadata 评论，不直接改数据库或伪造 done。

### 必填任务卡

```text
目标：<独立可验的用户结果；本卡具体完成线>
owner／执行身份：<唯一 writer、原生会话；PM 与集成执行者>
workspace：worktree；工作区／分支：<核实可用的位置>
允许路径：<精确文件／目录；只读审查填无>
只读要求：<是否只读；审查须绑定精确稳定 head 的独立快照，结束核未改>
红线：真实产品测试模型按当前授权仅用开发网关 GPT；独立已授权 Opus 审查不受此产品测试路由限制；不本地浏览器、不碰生产／真数据／未授权费用
parents：<前置卡 ID，无则明确无；对应就绪证据>
接口决定：<写卡会话起草输入／输出、owner、安全／失败语义；公共接口由集成者确认，变更重新确认>
共享独占项：<契约／锁文件／迁移编号／STATUS；不得自行写>
限定验证：<最近 unit 文件、所属包 types、必要集成与执行者；文档仅 diff>
风险：<L／H／U 及依据、目标分支；迁移与回退、权限／费用／取消影响>
Git 授权：<commit／push／PR base／是否可合；worker 不部署，部署由唯一集成者按“用户长期授权”第 3 条执行，否则单独审批>
预算：实现 1 次＋对应风险的独立审查各 1 次（L Opus 后补）＋必要集中修复 1 次
metadata：changed_files、commands＋真实 exit、results、commit、remoteSHA、PR、unverified、owner／是否交回
```

任务卡不能授权突破更高层限制。写卡会话先列出公开契约、schema、枚举、签名、版本／白名单、共用文件及数据可信来源，起草“接口决定”；公共接口由唯一集成者确认后才能派发，变更回集成者。计划内产品细则由 PM 按现有规则设默认值并在原账本记录，不把接口确认留给 worker 自行拍板；涉及产品方向、迁移或未授权事项仍交用户。共享接口未定先解决依赖，禁止各流分别写出不兼容契约。开发成本原则上不约束执行，不为压缩成本牺牲结果；但不改变产品费用策略、付费模型调用授权、预算规则、有效配额和运行资源限制，不购买额度绕过审查阻塞。

## 连续实施与验证准入

实现者在 allowlist 内连续完成一个可用结果，不为每个内部函数另建卡、PR 或评审。只加载当前所需文件与技能；恢复时核原卡、工作区、最新差异和直接缺验，不反复读长 STATUS／总计划。STATUS 由唯一集成者按实际交付更新，普通 worker 只读必要行。

- 实际隔离的文件与运行资源可并行编码／验证；共享环境重验证必须经现有 `run-heavy` 串行，不能只靠“不同 worktree”并跑数据库、类型或构建。不得停止或抢占其他任务。
- 轻量源码、语法、diff 与现成近邻检查先行；只跑本片直接相关 unit／包 types／集成，不先全套再定点。纯文档只审实际 diff 和规则一致性，不跑业务测试或服务。
- 本地资源不足时先限制新卡／工作树／重验证准入，不以本地全套、构建或大包 PG 阻塞已授权实施。完整类型、构建和测试门禁交现有远端 CI；未运行范围如实记 `unverified`，不能把定点 roots 绿说成包／依赖闭包绿。
- 已有验证在源码版本、输入、环境与覆盖仍有效时复用。新改动只补直接缺验；集成的新影响补相关检查，不把不相干局部绿相加成整体绿。
- 失败按 failure → cause → fix → recheck：保留红测、锁拒绝、超时与缺终态，足够诊断后只做最小修复，不盲重试或降低断言／安全 guard。真正隔离 worker 的并行仍须获准且服从当前配额。
- 实现 1 次、对应风险的审查各 1 次、必要集中修复 1 次后若仍受阻，返回最小阻塞和下一决策；L 的 Opus 后补仍须排队跟进，不滚动加派、重复全审或新建通用评测／Agent 框架。
- 事件驱动处理交回、审查／CI 变化或用户消息，不设定时器、不轮询、不 sleep；通知不是已验交。v2 截止为 2026-11-10 23:59 北京时间（15:59 UTC），截止前 12 小时停止新开 H，只修缺陷、合入、部署和验收；部署仍须原授权。代码完成、合入、部署与用户验收分别统计，进度每 12 小时由账本 owner 在现有位置记录；不为此另建账本或再全面盘点。

## 每 PR 正式审查与分支规则

用户 2026-11-08 采用开发流程 v2，并以 2A 确认 #264 按保守统一规则执行；以下覆盖旧双审前置和补丁等价免审提升方案，不把后者记为 11-06 用户授权。PM 在 PR 正文标明 L／H／U、依据与目标，有疑问按 H。独立 GPT 与指定 Claude Opus 5.5 high 的实际批准不能由实现者自审替代；不得降模型、拿空 verdict／工具错误／旧 head 批准放行。

| 风险与路径 | 目标与准入 |
|---|---|
| L：只改测试、只改文档、纯删除死代码且无行为变化 | 功能分支 PR 到 `integration/opening`；独立 GPT 批准＋精确最新 head required CI 全过后，唯一集成者可合入，进入指定 Opus 后补审队列。补审发现真实缺陷立即开修复 PR，优先级最高；不能把后补审标为已通过。 |
| H：改变行为、数据、契约或公共接口（包括 UI 行为） | 从安全基线独立 PR 到 `feat/opening-release`，不借 L 集成池带入；合入前指定 Opus 与独立 GPT 均批准＋精确 head required CI。涉及原有用户批准边界时仍保留 `needs_input`，满足下节长期授权全部条件的才视为获准，由唯一集成者合入。 |
| U：迁移部署、生产配置、真实数据、破坏性操作及用户保留的专项时机／规则决定 | 原有门禁＋用户确认，不因 L 或提升路径放宽。#264 四问已由 2A 决定，#230 时机按最新用户决定执行；不能由 Agent 自行推导新授权。 |
| 集成提升 | 唯一集成者将 `integration/opening` 已达标结果提升到 `feat/opening-release`；GPT 快审完整当前 base-to-head 差分＋精确 head required CI。所含 L 仍须 Opus 后补审，不因提升取消。 |

### 提升与后补审节奏

按 v2 每攒至少 3 个 L 合入，或距上次提升约 6 小时，批量提升，不逐个改动提升。提升仍由唯一集成者执行，正文列出完整 base／head SHA、所含 PR、原审查链接、额外集成差分及 L 补审状态；不能只凭补丁 hash 或旧审查免去 GPT 快审。base 或 head 变化后重新确认实际差分、审查覆盖和精确 CI。

提升不是 H 的替代入口；若冲突解决、集成者补改或所含内容新增行为、数据或接口变化，先回 PM 重新分级并补齐 H 门禁。L 的 Opus 不可用时保留队列和未审事实，不冻结无依赖 L 实施，也不以延期补审推导部署资格；部署继续按下节原有条件。

### 用户长期授权

用户于 2026-11-05 明确给出以下长期授权，2026-11-06 扩展第 1 条并新增第 3 条，有效至用户撤回。v2／2A 仅按上文调整合入路径、审查时点与分工，不扩张生产授权；接管也不产生第二合并权。授权只由唯一集成者执行，不扩展到其他角色。

1. **高风险 PR 合入 `feat/opening-release`**：在上表高风险门禁（指定 Opus、异家族审查、精确 head required CI、独立主线 PR）全部完成的前提下，同时满足以下条件时，视为已获用户明确批准，由唯一集成者按 expected SHA 以 merge commit 合入。用户 2026-11-06 决定两个模型都批准就合并，含迁移的 PR 也适用。
   - 指定 Claude Opus 5.5 high 与 GPT 异家族审查都对当前 head，或对相对 base 的完整 `--binary --full-index` 补丁 SHA-256 与当前 head 相同的已审版本，给出 approved，且没有未关闭的 blocking。
   - 当前精确 head 的 required CI 全部通过。
   - 合入内容与已审补丁逐字节一致。存在文件重叠的三方合并时补丁不再逐字节一致，本授权不适用：须对合并结果重新取得两个模型的审查，或由用户逐次批准。
   - 合入不等于执行：含迁移的 PR 合入后，包含该迁移的版本部署仍须用户逐次批准（见本节末）。合入也不构成生产配置生效的授权。
   - 每次合入都在 PR 正文记录所依据的审查、CI 和等价证明。
2. **清理**：已完全合入主线、相对主线没有独有提交、工作区干净的 worktree 和远端分支，可由唯一集成者回收。有独有提交、未合并、属于线上参照树或无法判断的，仍须用户决定。
3. **不含迁移的主线版本部署**（2026-11-06）：同时满足以下条件时，由唯一集成者用目标版本自带的受管发布脚本部署主线精确 head，不再逐次等用户批准。
   - 目标版本与线上版本之间迁移目录没有差异，并且部署前只读核实线上数据库的迁移账本已包含目标版本的全部迁移。核实只读 `schema_migrations` 中的迁移编号，不读业务数据、不打印连接凭据，只记录“目标版本的迁移已全部登记”或待执行清单。受管发布脚本会执行所有尚未应用的迁移，只比较代码目录不够；发现待执行迁移或无法确认时，按含迁移的版本处理，先取得用户批准。
   - 相对线上版本新增的每个 PR 都经两个模型批准；双模型门禁写入本文件（#260 合入 integration）之前只经指定审查合入 integration 的 PR，由包含它的提升 PR 的 GPT 审查覆盖。v2 允许 L 先合入后补 Opus，不自动放宽此部署条件，补审未齐不能据此直接部署。
   - 目标版本若改动了会写到服务器上的服务配置，部署前单独列出，按生产配置逐次审批。这包括 `infra/deploy/` 下的服务单元、容器编排和主机初始化脚本，以及 `deploy-hermes.sh`、`hermes-release.sh` 中写入 systemd override／drop-in 或决定其写入位置的部分；只改打包或校验逻辑的不在此列。
   - 目标 SHA 的 required CI 全部通过。
   - 部署前在会话中向用户给出精确提交号、迁移差异与回滚方案；部署后只读核验健康检查返回的提交与服务状态，结论按“公开仓库信息边界”记入 STATUS。

接手停滞车道按 2A 保守规则：先核原 owner 已停止写入且明确交回，PM 记录原卡、候选 SHA、写集合及新 owner 后续接，不以平台错误或等待时长自动接手，不 reset／覆盖原成果。接管只转移获准写权，不新增 integration／主线合并或部署权。

以下事项不在授权范围内，仍须用户逐次审批：含迁移的版本部署、迁移执行、生产配置、真实数据操作（含导出、改写）、破坏性迁移、定样。

接口或用途使风险升级时先回 PM／集成者调整原卡和依赖，不以文件少、测试过或分支名认定低风险。PR 写明全部相对 base 改动及未验范围；不能只描述最后一笔修复，也不能以旧候选已批准覆盖新 head。若合并目标变化或集成修改影响审查覆盖，重新确认实际差分和对应门禁，不静默沿用旧批准。

Git 使用 Conventional Commit，正式仓库为 `Xhhemoing/study-assistant-opening`，remote 命名为 `study-assistant-opening`（新克隆把 `origin` 改为此名），不推任何旧仓库 remote；commit、push、PR、合并及发布各自服从当前授权，禁止 force、reset／clean／覆盖他人成果。没有迁移的卡明确写无，不捏造回滚。允许的本地完成与代码交回不是已交付用户；最终合并和用户效果另记真实证据。

含迁移的版本部署、生产配置、真数据导出／改写、破坏性迁移、定样仍需用户审批；不含迁移的主线版本只按“用户长期授权”第 3 条部署。开发成本原则不解除产品费用策略或该审批边界。不得用“加快交付”推导发布授权。

## 浏览器、信息与按需工具边界

Agent 不自行或委派本地浏览器、Playwright、截图、真机验收；用户浏览器验收与 CI 浏览器分别报告。保持现有 CI 浏览器检查，不关闭或降门禁；待用户验收不冒称已过，也不阻塞独立后继开发。

工具按实际可用能力分工，不把历史“某工具不可用”或某次服务恢复当永久事实。模型与网关配置、密钥只留私有授权环境，不复制到仓库；公开文档不写主机地址、绝对运行路径、PID、生产拓扑或运维快照。只读审查不写业务，换执行者须明确 owner 已停写与交回（停滞车道同样适用 2A 保守规则），不把新会话当配额逃逸。

### 工具执行与只读审查

- 真实产品测试模型按当前授权仅使用开发网关 GPT 系列，不自行调用其他付费 API 或增加未授权费用。独立、已获授权的指定 Opus 审查属于审查门禁，不受产品测试路由限制；它仍须遵守当前渠道、模型、强度、配额和只读授权，不据此授予产品调用权限。
- 单次 CLI 审查运行不假设已加载 `AGENTS.md`。派单 brief 必须写全目标、允许路径／只读要求、生产与真数据禁区、本地浏览器禁令、模型／费用授权和 Git 操作边界；不得仅给文档链接代替红线。
- 指定审查绑定精确、稳定的 PR head，使用该提交的独立干净快照；送审期间不改候选。审查开始记录完整 SHA 与干净状态，结束核对 SHA 未变、检出及暂存区未被修改（包括非预期新增文件）；有变化先报告，不能把它当作原候选的只读批准。其他互斥工作可继续，但不共享该审查快照写权。
- 工具只按当前获准且实际可用的能力运行，不恢复历史工具名单或旧路由。模型与网关配置、密钥保留在仓库外私有授权位置，凭据仅经获准环境或秘密存储注入，不写入 brief、公开日志或仓库。

### 图谱按需维护

图谱用于定位和导航，不作为日常完成门禁。源码变化后，若已有 `graphify-out/graph.json`，沿根 `AGENTS.md` 规则设置 `graphify-out/needs_update`；纯文档／注释改动不刷新。查询前检查陈旧标记；stale 图只作历史导航，当前调用链、依赖和影响范围必须回读现行源码，不借用其他版本的图冒充当前关系。

只有当前授权涵盖且确有刷新需要时，才在对应有效工作区运行一次 `graphify update .`，等待终态并记录失败／未完成；用户明确要求刷新同样服从写权与资源准入。不得按每个任务、提交、状态回复或批次自动刷新，也不静默启动后台更新，完成前不把旧图说成新图。

已有结构图仅需重算社区／图分析时，可按授权运行 `graphify cluster-only . --no-label`（不调用模型）：它只更新 graph／report 及可生成的 HTML，不更新 wiki 或 manifest；其他导出须按需单独生成核对。刷新期间禁止并发 Graphify 写入；禁止用 `--force` 绕过缩减保护，也不得以跳过关系清理的原始 `--no-cluster` 输出代替正式图。图谱位于忽略的 `graphify-out/`，不提交到仓库。

图谱不减少源码、适用检查、独立审查及 CI 的要求。纯文档不新建 evidence／baseline／费用账本或状态平台；持久任务事实在原 Kanban，项目交付摘要由唯一集成者写 STATUS，worker 收工在原卡交回结果与未验项，二者不互相伪造完成。

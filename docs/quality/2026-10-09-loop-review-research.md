## 3. 用学生的一天检验闭环，而不是按菜单数量判断项目

建议把核心体验固定为一条路径：

**接收并确认信息 → 安排今日 → 学习与尝试 → 记录证据 → 延迟独立复测 → 调整明日 → 周复盘。**

课程、生活安排和项目目标共用这条路径。课程是组织容器，不应成为唯一入口；学生临时遇到一道题、一项社团任务或一封课程邮件，也应该能在同一任务与证据模型中落地。以下是产品验收设计，不代表每项现有实现都缺失。

| 场景 | 系统应该做什么 | 不应该做什么 |
|---|---|---|
| 早上查看一天 | 在已确认课程、睡眠、吃饭与通勤之外安排有限行动，说明为什么现在做 | 把所有积压任务塞进今日，以“排满”制造虚假效率 |
| 教师邮件出现新 DDL | 绑定来源与版本，提出待确认任务，接受后进入计划 | 将未确认的 AI 提取结果直接视为正式截止时间 |
| 课间只有 15 分钟 | 提供适合短时段的复习/回忆；无法放入的大任务明确未排 | 擅自拆解必须连续完成的实验或写作任务 |
| 学生先自己做题再求助 | 保留首次作答，渐进提示，标记参考/答案暴露 | 把看到答案后的正确回答记成独立掌握 |
| 下午有延迟复测 | 不早于允许时间，且保留独立性要求 | 因为“今天到期”就排到上午 |
| 晚上太忙、跳过任务 | 询问极简原因，提出降载草稿，保护固定生活安排 | 把一次跳过解释为能力下降，或自动延长学习到深夜 |
| 次日重新打开 | 继续上次上下文，展示反馈已影响的下一步 | 只存一份总结，却让今日队列仍按旧状态运转 |
| 周末复盘 | 区分完成、独立正确、延迟保持和负担；暴露未知状态 | 用对话次数、卡片数量或单一“掌握率”替代学习效果 |

可以采用一个混合课程学周作为小规模真实验收：一门计算课程、一门阅读/写作课程、一项实验或社团任务。先验证系统是否减少漏项和切换成本，再评价学习效果；不能用一种题型的改善外推所有大学课程。

## 4. 本次直接修改并提交的内容

提交：`fix(tooling): reject incomplete local readiness checks`。[G02]

修改文件：

- `scripts/opening-local-check.mjs`
- `scripts/opening-local-check.test.mjs`

第一，原评估器只要求端口集合非空且返回项都成功，部分结果也可能误判为全通过。现在要求六个既定端口的名称与端口号完整匹配，再判断全部成功。

第三，原 readiness 只要求有条目且 `ok` 为真。现在每一项必须有非空字符串标识，拒绝空身份、缺失条目与非布尔成功值，避免不完整报告虚假变绿。

第四，保留环境值与 readiness detail 的脱敏，新增成功路径的泄露回归检查。这不是对所有日志泄密情形的完整安全审计。

## 5. 优先级最高的大问题与具体方案

### 5.1 P0：发布状态必须是同一提交的证据集合

“任务 verified”“CI 通过”“真实环境可用”“用户验收完成”是不同事实。最新台账还保留 Q03/RP5 active 和 Q01/Q02/Q04 planned；最新 CI 37938933772 已失败于计划与工具检查，因此不能把整项目标成已交付。上一轮 37937794431 的两个 lint 错误已经由并发提交 f1e6ea0 修复，不能重复记作当前失败原因。当前失败步骤的详细根因尚未取得。[G09][G10][G01][G05]

建议建立发布证据索引，而不是增加一层复杂工作流引擎。每条证据最少包含 `commitSha、checkName、runId、environment、completedAt、result、artifact`。无证据显示 unknown；旧提交通过显示 stale；运行中显示 pending；失败保留定位入口。凭据不进入状态 JSON。

执行顺序为：RP5 收敛 CI；Q03 补全备份恢复和打包证据；满足依赖后推进 Q01 → Q02 → Q04。恢复演练应在新的隔离命名空间中完成，核对数据库记录与对象存储对象、来源版本和可用引用，不能只证明“打包命令返回 0”。是否已覆盖某项，应逐条读取当前证据文件确认，而不是因 Q03 仍 active 就否定已有恢复实现。

验收门槛：最终发布候选的源码 SHA 与所有要求的自动化/人工证据一致；发生影响范围内的新提交后重跑相关检查，不能直接继承旧总绿灯。此建议不要求用户现在就做生产切换。

上一轮 CI 的 npm 安装输出还报告了 54 项依赖漏洞告警（32 moderate、20 high、2 critical）。这只是该运行的依赖审计计数，不等于 54 个可利用的线上漏洞，也不代表已完成逐项分析。应保存 advisory / 依赖路径 / 运行时可达性 / 可用补丁的清单，优先核实生产依赖中的高风险项；不要直接执行 `npm audit fix --force` 破坏锁定版本与兼容性。[G10]

### 5.2 P1：排程器漏掉补测的最早执行时间

这是本次在最终版本中确认的源码问题。`packages/domain/src/opening/day-planner.ts` 中，`isRetestNotYetDue` 判断 `recommendedAt > dayEnd`，用来过滤非当天补测；真正分配时间时寻找 `candidate.start + duration <= min(candidate.end, due)`，没有取 `recommendedAt` 与候选开始时间的最大值。[G04]

**代码推导反例，尚未运行领域测试：**某补测 `recommendedAt=今天16:00`、耗时20分钟，上午09:00有空档，截止时间允许。它不会被“晚于日末”过滤掉，之后可能被安排到09:00。即便后端独立性检查最终拒绝早测，学生仍会看到一个不可执行或无效的推荐；如果后端也未兜底，则会污染延迟证据。

建议将时间约束显式化：

```text
start = max(slot.start, task.notBefore, planningNow)
end   = start + duration
要求 end <= min(slot.end, task.dueAt)
```

真正实现时不能只改这一行。选择未来时间段后，原空档的前缀要保留给其他任务，否则下午补测会浪费上午时间；同时兼容 confirmed deadline、preferredOrder、不可拆分任务和固定安排。在提交复测结果时再次由服务端核验最早允许时间，前端禁用按钮不构成保障。

补充测试：下午补测不早排；仅上午空档时未排且原因明确；存在下午空档时正确安排；晚测不阻塞其他可在上午完成的任务；恰好到期边界；超过截止时间；无可用时间；并发接受旧草稿。计划提案不能自行修改任务完成状态，这是当前源码值得保留的边界。[G04]

### 5.3 P1：日边界必须与课表、工作区时区共用同一解释

当前 `resolveDayEndMs` 在未传 `options.dayEnd` 时，取最早 free 开始时间的 UTC 日期并拼接 UTC 日末。这个默认行为不保证等于学生本地日期的结束。调用端可能已显式传值，所以本次不把它判成已证实的所有用户错误，而是明确的跨模块契约风险。[G04]

建议每次计划请求携带本地日期和工作区时区，由一个地方计算 `[dayStart, nextDayStart)`；存储时间用绝对时间，展示与课表展开按工作区时区处理。非法日期应报可理解的输入错误，不能让 NaN 或无限边界悄悄退化成不约束。

应补性质测试：上海与负偏移时区、跨夜安排、不同季节偏移、课程例外、紧邻不重叠块、重复/重叠 free 块不增加虚假容量。这里对重叠块的要求是验收建议；本次没有独立确认 `availableTimeSlots` 的全部实现，不能沿用旧版本对它的缺陷推断。

### 5.4 P0：预算安全门禁、费用回执和调用方契约一致性

审查取得的历史 CI 失败信息涉及缺少单次预算、费用明细要求、错误分类不符、失败/重试后的预算占用等多类问题。它们不是一个可以靠删除断言解决的小错误，而且历史运行不能直接代表最新提交。[G07]

正确处理顺序是先按真实错误族分组：生产调用方是否遗漏参数；测试 fixture 是否没跟随强制字段升级；禁用能力/额度不足是否在错误映射中变成泛化 INTERNAL；provider 用量回执是否缺少必要维度；异常发生在请求发出之前还是之后；重复或迟到回调是否重复记账。

建议确立一套共同契约：允许能力、单次费用上限、工作区余量、预计最大调用次数、provider 执行凭证和实际费用确认状态。字段与现有命名兼容，避免再造一套并行预算模型。失败分清三类：未发出请求可释放对应预留；已发出且费用已知按已知事实结算；已发出但费用未知保留待对账，不以 0 费用强行清空。重复执行的最终状态应与一次成功执行一致；这是 BullMQ 对可重试作业的官方设计要求。[R03]

最低测试矩阵：缺少单次预算时 provider 调用数为0；禁用能力优先返回稳定业务错误；合法 fixture 通过全部必需字段；两个并发请求不能同时消费同一余额；取消与迟到结果竞争不会双扣/双退；provider 调用成功但本地持久化失败可恢复；细分 usage 不完整时保留对账状态；未知费用经人工或自动确认后只收敛一次。

先在最新候选 SHA 重跑失败族，再决定修生产代码还是 fixture。本文没有把历史失败计入最新发布的测试失败数，也没有为了跑绿而放宽预算保护。

### 5.5 P1：学习智能化的单位应是可解释证据，不是单一掌握百分比

最新台账已覆盖复测、自测、参考暴露与能力证据，所以建议是整合、验证与增量优化，不是另起一个学生模型。[G01]

学习态建议分层：接触过、辅助完成、独立完成、延迟保持、迁移表现；没有足够证据就是待检验。每次作答记录关联 `goal/skill、sourceVersion、attempt、hint/reference exposure、rubric、retest、nextAction`。不要求立即增加所有字段：先审查现有等价字段，以迁移最小化为原则。

界面应分别呈现“今天完成了什么”和“什么已经有独立证据”。使用 AI 后答对可以证明一次有辅助练习完成，但不能自动证明独立掌握。延迟复测后，弱项与任务优先级应真的发生变化；要验证读模型与下一日建议是否消费了事件，而不是只写入一张记录表。

PNAS 2025 年一项高中数学现场实验发现，无护栏 AI 辅助练习的即时表现与移除 AI 后的独立表现并不等价，提示式护栏能缓解其研究情境中的不利影响。这支持“先尝试、渐进提示、再独立检验”的设计方向；研究来自特定高中数学情境，不能把其效应量外推为本项目对大学生的提升预测。[R01]

复习方面，不建议把目标保持率一味拉高。Anki 官方手册明确说明 FSRS 中更高目标保持率意味着更多复习负担，并要求把真正遗忘与费力回忆区分。项目应先保证诚实、可区分的复习记录，再谈个体化参数或更复杂的知识追踪。[R02]

### 5.6 P1：生活闭环的智能应该优先体现在减负与可拒绝

在已有课表和每日草稿之上，优先增加或核验三个策略：固定生活安排是硬约束；重复跳过产生可解释的降载建议；所有重大变更仍是 proposal，由用户确认。模型只提出解释和候选，不直接改正式截止日期、不自动向老师或同学发消息、不自行接受社团事务，也不从学生疲劳描述推断健康诊断。

跳过原因可先保持四类：没时间、太难、任务已无意义、暂不想做。它们分别触发重排/拆分建议、降低任务粒度或先修补、关闭确认、保留选择权。不要一次跳过就永久下调目标或能力；需要跨日证据，并允许撤销建议。

“今天更智能”的最低标准是：推荐与学生真实空档相容；知道自己没有足够证据；能解释未排事项；能从昨天的反馈改变今天，而不是对话写得更长。

## 6. 架构优化：沿用已有分层，补齐跨层不变量

建议延续 monorepo 中已有 web / API / domain / database / worker 的职责方向，不为本轮目标引入新的 Agent 编排大框架。新增能力应围绕同一任务、来源和证据标识工作。[G04][G06]

领域层负责纯约束和状态转移；API 层负责权限、输入边界、确认语义与幂等；数据库保存版本化事实与必要事务；worker 负责可恢复的外部调用和长任务；web 负责下一步行动及来源解释。只要已有实现符合这些职责，就不要因为“智能化”重复拆分。

建议逐条验证五个不变量：一份 source 的新版本不能悄悄给旧引用换内容；撤销连接后迟到作业不能重新写入有效学习资料；完成行动不直接等于掌握；补测时间与独立性在服务端有效；未知实际 AI 成本不被提前清零。前两项是重要验收要求，不是本轮已证实的最新缺陷。

状态看板的长期接入可复用项目现有能力入口：构建时生成非敏感 evidence JSON，以一个只读管理视图展示，不让浏览器直接携带 GitHub 写令牌。学习首页保持少量关键数字和下一步；工程状态面板只面向维护者。此次交付的是独立离线 HTML，并未改动现有应用路由，也未声称新建了线上仪表盘。

## 7. 子 Agent 工作包（未执行的建议分工）

本会话没有可调用的子 Agent 执行器。以下是接入执行器后可直接采用的工作拆分，不是多 Agent 的执行记录。

| 工作包 | 读取/修改范围 | 交付物 | 验收与写入边界 |
|---|---|---|---|
| A：预算与可靠性 | 预算调用链、费用回执、错误映射、worker/queue 测试 | 最小复现、调用方/fixture 分类、聚焦补丁、日志 | 不移除安全门禁；共享契约改动先经集成器批准 |
| B：规划与生活约束 | day-planner、时间块、课表、每日草稿相关契约 | notBefore 与时区方案、领域测试、迁移影响 | 不自动改 confirmed plan；保留未排原因 |
| C：学习证据与体验 | 作答/暴露/复测/技能证据、今日读模型 | 状态图、读写一致性测试、界面验收清单 | 不以点击完成替代掌握；不越权处理私密资料 |
| D：集成与发布 | Q03/RP5→Q01→Q02→Q04、工作流与证据索引 | 单一候选 SHA、恢复证据、发布与回退说明 | 唯一分支集成者；非强制快进/CAS；人工验收 |

每个工作包先固定基线 SHA，使用独立分支或 worktree，先交“发现与证据”，再交补丁；集成器核对新 HEAD 后合并。不让两个 Agent 同时修改同一契约文件或任务台账，不用模拟对话冒充真实并行审查。每个完成声明必须附命令、退出码、SHA 与产物。

## 8. 可执行的两阶段推进计划

以下是建议顺序，不是已经承诺或测量过的工期。

**第一阶段：收敛一个可交付候选。**固定候选 HEAD，先获取 Plan and tooling checks 的失败日志并最小复现；将当前故障与历史预算/回执失败分开归类；保留本次检查器补丁；补齐排程最早时间测试；验证 Q03 的恢复与打包剩余项；完成同一 SHA 上的必要门禁。验收前不做大规模框架重构。

**第二阶段：一个真实学周的闭环检验。**在使用者授权的测试环境，用真实课程节奏但最小必要的数据，串联信息接收、安排、学习、辅助、自测、延迟复测、次日调整；逐次记录掉链点。然后再决定是否增加知识图、更多连接器、FSRS 参数优化或个体化模型，而不是先把系统复杂度堆上去。

| 建议指标 | 口径 | 为什么需要 |
|---|---|---|
| 约束违规数 | 排程侵入固定安排或早于 notBefore 的次数 | 是错误，不应通过“总体平均好”掩盖 |
| 可执行建议率 | 推荐出现时满足时间、权限与预算条件的建议占比 | 衡量建议是否真能执行 |
| 独立延迟复测结果 | 与辅助练习分离，注明时间与内容 | 不被 AI 辅助即时成绩混淆 |
| 未排与逾期趋势 | 区分没时间、太难、无效任务等原因 | 识别负担，而非单纯催促 |
| 用户否决/撤销原因 | 记录建议不合用的具体类别 | 为渐进个性化提供反馈 |
| 故障后的恢复完整性 | 数据/对象/引用/费用状态是否一致 | 决定能否长期托付 |

这些是拟采集指标，目前没有生产数据，不能填写提升百分比。样本小也不能把短期变化当成因果结论。

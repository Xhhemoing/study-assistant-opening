# Brainstorm 研究与算法候选库

`docs/brainstorm/` 专门保存项目对话中产生的调研结果、问题分析、候选方案和算法优化依据。它让重要思考可以被追踪、复用、验证和升级，而不是散落在聊天记录中。

## 1. 文档权威边界

Brainstorm 文档不是已批准需求，也不是实现规范。

```text
项目对话与外部调研
→ docs/brainstorm（证据、假设、候选方案）
→ docs/plans（经用户批准的产品/实施设计）
→ docs/decisions（重要且难逆转的架构决策）
→ 代码、测试与运行证据
```

- `brainstorm` 可以保留互相竞争的方案、未验证假设和失败方向。
- 进入实现前，结论必须明确提升到对应的 `plans` 或 `decisions` 文档。
- Brainstorm 不得静默改变 PRD、已批准设计、ADR 或当前实施顺序。
- 已被新研究取代的文档不删除，标记 `superseded` 并链接替代文档。

## 2. 目录内容

- `INDEX.md`：研究登记表、状态和正式落点。
- `ALGORITHM_MAP.md`：项目各板块的目标、基线算法、扩展路径和评估指标。
- `templates/research-note.md`：新增研究记录的统一模板。
- `YYYY-MM-DD-<topic>.md`：一次对话或专题调研的结论。

附件、实验结果或较大数据集应放在对应专题子目录，并在研究记录中链接；不要把不可追踪的数据直接粘贴到结论中。

## 3. 何时必须记录

出现以下任一情况时，应新增或更新 Brainstorm 记录：

1. 项目对话形成了可复用的产品、架构、算法或交互结论；
2. 比较了多个算法、框架、模型、协议或外部产品；
3. 发现现有设计与实现之间存在断层；
4. 形成了尚未批准但会影响多个任务的候选方向；
5. 实验失败、结果不符合预期，且原因对后续选型有价值；
6. 新数据推翻、限制或扩展了原有假设。

简单事实查询、临时任务进度、已完成工作的流水账不进入该目录。

## 4. 研究记录要求

每份记录必须说明：

- `status`：`exploring | proposed | validated | promoted | superseded | rejected`；
- `scope`：明确指向产品板块、领域对象、包、应用或计划任务；
- `question`：要解决的决策问题，不只记录资料摘要；
- `evidence`：官方文档、代码、实验或用户场景；
- `facts / assumptions / proposals`：三者分开书写；
- `options`：至少列出当前基线和主要替代方案；
- `evaluation`：效果、成本、延迟、可解释性、隐私、可移植性和扩展性；
- `recommendation`：推荐方案、适用边界和不采用条件；
- `validation`：数据集、指标、基线、通过阈值和回退条件；
- `promotion target`：获批后要更新的 PRD、plan、ADR、contract、schema 或 task。

涉及外部现状时标注调研日期。无法从可靠来源验证的结论必须标为假设，不能伪装成事实。

## 5. 算法与做法选型门槛

“尽可能效果好且可扩展”不等于默认采用最复杂的模型。每个板块都必须先定义目标函数、约束和评价方法，再选择最简单且达到门槛的方案。

算法提案至少回答：

1. 优化的用户结果是什么；
2. 输入、输出和不可违反的不变量是什么；
3. 当前规则或启发式基线是什么；
4. 候选高级算法为何可能更好；
5. 用什么离线指标、线上指标和用户验收判断；
6. 数据不足、模型失败或基础设施不可用时如何降级；
7. 如何版本化、解释、重算、迁移和回滚；
8. 在什么数据量、延迟或复杂度门槛下才升级方案。

禁止仅因流行、理论先进或模型规模更大而替换可靠基线。预测、排序和推荐必须与明确事件或用户结果一一对应，不能优化含义模糊的“参与度”或“掌握度”。

## 6. 评审与提升流程

1. 使用模板记录问题和证据。
2. 更新 `INDEX.md`，注明指向板块和负责人状态。
3. 对高影响结论完成最小 Spike、回放评估或用户场景验证。
4. 用户批准产品方向后，提升到 `docs/plans/`。
5. 难以逆转或影响多个边界的技术决定写入 `docs/decisions/`。
6. 实现时引用对应设计和 Brainstorm 记录，并以测试和运行结果验收。
7. 上线后将真实指标和失败模式回写研究记录，必要时创建后续研究。

研究记录可以被实现验证，但不能用“已有文档”代替真实测试、基准或用户验收。

# study-assistant-opening 二次开发计划
## 从“材料辅导工具”升级为“AI 主讲的全流程学习伙伴”

**二次开发的核心目标应正式确定为：用户带着材料、主题、问题或目标进入，由 AI 组织并呈现主要教学内容，陪伴用户理解、思考、实践、纠错和复习；原材料作为可追溯依据，实际学习表现推动下一步，用户始终拥有改变路径和节奏的权利。**

## 一、把已经达成的共识转成开发约束

这些不是“尽量做到”的附加要求，而是用于判断后续任务是否走偏的标准。

| 开发目标 | 必须交付的行为 | 不能接受的替代方案 |
|---|---|---|
| **AI 组织并呈现教学** | 进入后就能开始有结构的讲解和学习活动 | 必须先翻原文、选段落、自己想好问题，AI 才有作用 |
| **陪伴完整学习过程** | 理解、探索、实践、反馈、沉淀、复习、继续之间保持联系 | 多个功能各自存在，用户反复搬运材料和交代背景 |
| **用户保留自主性** | 可以跳过、追问、看完整讲解、改道、暂停、结束 | 强制测验、强制苏格拉底追问、答错就不能继续 |
| **介入可个性化且可靠** | 时机、频率和帮助深度可设置，并根据分型反馈调整 | 仅凭停留时间判断卡住，或用点赞推断学会 |
| **表达清晰且按需互动** | 文字、公式、图示、演示服务于当前理解任务 | 一味生成长讲义，或用大量动画制造表面丰富 |
| **学习证据不夸大** | 区分已阅读、受助完成、独立完成、延迟表现与迁移 | 将完成度、满意度、看过解析直接记成掌握 |
| **学习可以自然接续** | 恢复材料、思路、草稿、尝试、帮助和下一步 | 只是重新打开聊天窗口 |
| **增量改造现有项目** | 复用已有事实、权限、预算、版本和执行机制 | 推倒重建、复制评分系统、绕过现有质量要求 |

这里需要明确一个取舍：

> **AI 主讲不等于 AI 控制；完整陪伴不等于强制完整流程；个性化不等于迎合所有即时反馈；可追溯不等于原材料永远正确。**

课程、笔记、阅读器、知识库和计划器继续保留，但围绕学习过程提供支持，不再争夺产品中心。

## 二、本轮核查后的项目判断

本轮重新核查的开发基线仍是 `feat/opening-release`，提交 `1a4cf465c86da7f08b6fda3044f9b0f932b80824`，提交时间为 **2026 年 10 月 10 日**。以下对代码现状的判断绑定这个版本，不把旧报告里的问题直接当作现在仍然存在的缺陷。

### 1. 项目不是缺少所有基础，而是缺少把基础组织成教学体验的核心层

现有学习契约已经区分了正确、错误、未核验、帮助程度、判断来源、题目与材料版本、观察修订等信息；worker 也已经具有持久任务、来源版本、历史上下文、预算调用和隐私版本检查等机制。这些应作为二次开发的基础，而不是再建设一套平行系统。

**我的判断是：主要需要增加“连续教学的组织与呈现”，同时修正已有机制在 AI 主讲场景下不再合适的语义。**

### 2. 已核查的关键改造点

| 当前实现或边界 | 对新目标的影响 | 二次开发的处理 |
|---|---|---|
| 学习会话创建仍要求 `courseId`、`skillLabel` | 自由问题、无课程探索不能直接套用这条会话路径 | 增加可自由开始的活动上下文，并兼容原有事实写入 |
| 部分辅导推荐依赖 `currentPage` | 页面操作容易成为教学开始的前提 | 新教学入口从目标和活动出发，由系统寻找依据 |
| `explain` 按模式映射为 `revealed` | 概念讲解与针对某题透露答案容易混淆 | 区分教学说明和作用于具体题目、尝试的帮助 |
| 重测缺少维度时默认 `transfer` | 延迟可能被当成迁移 | 分开记录延迟条件与迁移要求，缺信息保留未知 |
| 题目变式辅助函数主要改变引用字符串 | 新 ID 本身不能证明新题 | 按实际题目内容、版本及与旧题关系核查 |
| 引用检查包含软过滤与页码偏好 | 引用合法不代表讲解中的主张得到支持 | 新教学内容增加主张支持关系与范围覆盖检查 |

前两类会话与辅导边界可以从当前契约和策略代码直接看到；帮助映射也实际进入了 worker 的写回准备流程。

重测默认维度为 `transfer`、按标签寻找第一个匹配节点，也仍存在于当前源码。这些是需要调整或核实上游保证的边界，**不等于本轮已经复现了生产环境中的错误掌握判断**。

### 3. 交付基线需要先收口，但不能吞掉产品开发

当前提交的 CI 仍为失败。本轮读取的作业日志将失败定位到 `material-library.tsx` 中缺失的 `react-hooks/exhaustive-deps` 规则定义；对应源码确实存在该规则的抑制注释。后续主要检查未在该次运行中完成。

应当做最小修复、重跑真实失败，再按照现有流程完成检查。**不能通过关闭 lint、删掉浏览器检查或者改写完成状态来获得“绿色基线”。**

同时，仓库明确要求小范围验证、增量交付，并规定浏览器验收由用户负责；二次开发继续遵循这些约定，不另外建立一套重复的验收制度。

## 三、实际研究之后，哪些设计值得采用？

### 1. 论文支持的是教学设计与验证方法，不是自动生成课程的效果保证

| 研究依据 | 对项目有用的结论 | 对应开发决定 |
|---|---|---|
| **Bastani 等，PNAS，2025** | 辅助阶段表现提高，不一定转化为撤去辅助后的能力；教学保护需要认真设计 | 作答、帮助和独立结果分开，不能只优化满意度和当场正确率 |
| **Kestin 等，Scientific Reports，2025** | 经过教学设计的 AI 辅导在其大学教学实验中表现出积极结果 | AI 主讲值得做，但必须有目标、结构、反馈与真实验证 |
| **Koedinger 与 Aleven，帮助困境研究** | 给多少帮助、何时给，需要考虑具体情境 | 不固定“永远不给答案”或“一错就完整讲解” |
| **提取练习与间隔研究** | 适当的回忆与间隔安排有助于之后的保持；间隔与保持目标有关 | 提供可选独立尝试和延迟回顾，不把统一默认间隔说成个人最优模型 |
| **多媒体学习研究** | 学习者控制分段、必要的前置说明和相关表达具有设计价值 | 可暂停、可回看、同语义图文，不追求动画数量 |
| **2026 年《AI Assistants Overassist》预印本** | 模拟评测提示模型可能介入过早、过频繁，并给出过多完整解法 | 将介入决策从自由生成中分离，允许延后与不介入 |

上述依据分别来自原始研究出版页、作者摘要或可访问正文。它们的适用情境不同，尤其最后一项以模拟评测为主，不能替代真实学习者实验。[DOI](https://doi.org/10.1073/pnas.2422633122)

因此，本项目应采用：

**研究支持的初始规则 → 可解释的产品实现 → 真实使用验证 → 谨慎调整。**

而不是先设定一个“最佳介入频率”，再寻找论文为它背书。

### 2. 参考项目：借鉴机制，不照搬整套平台

**DeepTutor** 值得借鉴的是从结构到类型化内容、局部修改，以及内容与个人学习状态分离的方式；**OpenMAIC** 值得借鉴的是将教学提纲转化为不同教学场景的组织思路。它们的官方项目说明是实现参考，不是本项目已经获得学习效果的证据。[GitHub](https://github.com/HKUDS/DeepTutor)

对于动态界面，**A2UI 与 json-render 的声明式组件目录**提供了合适的工程方向：模型选择允许的组件和参数，程序负责渲染及动作执行。首版不必采用完整协议，也不应把引入某个框架当作目标。[A2UI](https://a2ui.org/)

我的建议是：

> **先在现有 React、TypeScript 和契约体系中实现一个小而可靠的教学组件目录。是否引入外部库，通过兼容性试验决定。**

这比先建设一个能生成任意网页、任意动画的系统，更贴近当前目标。

## 四、二次开发后的产品，应当怎样运行？

### 1. 用户进入后，直接获得可开始的教学

用户可以上传材料，也可以只提出一个主题或问题。系统根据已知上下文提出一个小范围学习方向，然后开始当前活动，不要求先完成课程创建、知识点维护或长问卷。

例如，进入“秩与零空间”后，AI 可以直接提出：

> 为什么二维输入经过某个线性变换后，只剩下一个输出方向？

随后呈现相关解释、可操作示例和必要定义。原材料保持可查，但不是学习必须先经过的入口。

**整体提纲可以查看，当前内容充分准备，后续活动逐步展开。**不必等待整门课生成，也不应每轮临时换一个教学方向。

### 2. 用户改变需求时，改当前活动，而不是重开一场聊天

“换一种解释”“完整推导一下”“更直观一点”“我先自己做”“跳过这一段”“回到刚才的问题”，都应该成为当前活动中的操作。

局部修改产生新版本；用户草稿、已做尝试、材料位置和之前的解释不被悄悄覆盖。

这样，用户获得的是一段可持续的学习，而不是不断追加、越来越难回看的聊天记录。

### 3. 暂停时保存学习断点，回来后能直接继续

断点至少需要保留三层内容：

**位置。**正在学习哪一活动、哪一内容版本、哪一个步骤或互动状态。

**思路。**用户实际提出的问题、写下的尝试、接受过的帮助，以及尚未解决之处。

**行动。**回来以后能够立即继续什么，而不只是看到一段摘要。

生成总结可以失败，但保存草稿和恢复学习不能依赖总结生成成功。

## 五、技术方案：新增教学组织层，不另造学习平台

### 1. 明确五类对象的职责

| 对象 | 负责什么 | 不负责什么 |
|---|---|---|
| **学习活动上下文** | 当前意图、材料范围、可选课程、路径和断点 | 自动宣布掌握 |
| **教学单元与活动定义** | 教学目标、内容块、来源关系、呈现方式和验证状态 | 复制用户成绩账本 |
| **统一内容与版本存储** | 教学正文、笔记、草稿各自的权威版本 | 在多个表中无差别复制正文 |
| **原有尝试、观察与帮助记录** | 实际学习事实与核验信息 | 把点击和完成度当成绩 |
| **只读学习过程视图** | 将已有事实组织成“发生了什么、接下来做什么” | 再建一套评分系统 |

项目旧实施指南已经强调：学习过程视图应复用事实与资格判定，避免以新功能名义创建平行系统。这一点与当前 AI 主讲方向并不冲突，应继续保留。study-assistant-opening-impleme…

### 2. 无课程入口需要兼容设计，而不是简单修改一个字段

现有正式学习接口要求课程关联，所以不能只把前端课程选择框隐藏就宣称支持自由学习。

建议的方案是：

新学习活动始终有 `workspace + owner + activityId`，课程可以为空；新的活动范围观察仍进入统一事实写入服务。旧接口保持原有课程要求，通过兼容适配接入同一套实现。

**不伪造一个用户看不见的“默认课程”，也不为无课程学习另外保存一套无法合并的作答事实。**

这涉及跨包契约、SQL 约束、权限、备份和历史兼容，应先做一个范围明确的架构决定，再实施迁移。迁移编号由项目集成者分配，本计划不预占。

### 3. 教学生成采用分阶段流程

建议流程为：

**学习意图与允许的上下文 → 授权来源包 → 小范围教学提纲 → 当前教学活动候选 → 内容核验 → 持久化版本 → 受控呈现 → 用户尝试与反馈 → 下一步候选。**

其中：

模型提出讲解、例子、活动与反馈；程序负责授权、版本、预算、组件执行和记录。正式学习判断仍依赖已有事实与适当核验，不由生成教学内容的同一条回复顺手写成“已掌握”。

现有 worker 的持久执行、预算和隐私机制可以复用，但新任务必须补充活动版本、取消、晚到结果及恢复的测试。

### 4. 生成状态与学习状态必须分开

“正在生成、待核验、可以使用、失败、结果未知、取消、来源失效”，描述的是内容状态。

“正在学习、暂停、完成、跳过”，描述的是用户进度。

**两类状态都不能直接转换成能力判断。**用户跳过一个活动，不等于做错；模型成功生成一节课，不等于用户学会。

## 六、三个必须优先做深的机制

### 机制 A：教学内容的可靠性

不能只检查 JSON 正确，也不能只检查引用 ID 存在。

建议依次检查：

**结构是否可执行。**组件类型、参数、长度和动作是否在允许范围。

**来源是否真实可访问。**属于正确用户、正确材料版本，页面或时间片段能够定位。

**主张是否得到支持。**引用内容是否真的支持结论，是否遗漏关键条件，是否只是模型推断。

**适用内容能否进一步核验。**计算使用实际计算检查；代码使用隔离测试；开放证明和作品保留无法自动确定的范围。

**是否仍可发布和继续使用。**来源撤回、隐私变化、版本冲突后，旧内容不能继续被当作当前可靠依据。

这些检查是不同层次。模型自报高置信、另一模型同意、格式完整，均不能单独替代事实核验。

### 机制 B：可靠的介入与反馈适应

首版就应提供显式偏好，推测性适应后续再增强。

设置优先级为：

**本次学习临时设置 > 课程或领域设置 > 全局默认。**

在内部，主动程度、允许节点和帮助深度分别处理。用户要求帮助时，即使处于安静模式也应回应；用户只是停留较久时，不自动判定卡住。

反馈也必须分型：

| 反馈 | 应调整 | 不应调整 |
|---|---|---|
| 现在别打断 | 时机和本次提示密度 | 学科能力 |
| 提示太多、透露答案 | 帮助深度 | 对整个学科的兴趣 |
| 换一种解释 | 表达、例子和推导方式 | 固定“学习风格”标签 |
| 你的判断不对 | 暂停使用该判断并核查 | 仅降一点权重后继续断言 |
| 这次有帮助 | 类似情境下的偏好候选 | 掌握状态 |

**明确偏好可以快速调整，教学效果判断必须慢一些。**

首版采用可解释规则，不直接部署用点击和点赞在线训练的黑箱。研究也并未给出可直接套用的统一介入频率。[Springer](https://link.springer.com/article/10.1007/s10648-007-9049-0)

### 机制 C：教学、帮助与独立表现的区别

这部分需要在 AI 主讲上线前完成，而不能事后补救。

**概念讲解是正常教学。**它不能自动使整个知识点以后所有题目都变成“受助作答”。

**针对某题的提示或解法，需要绑定实际题目与尝试。**同题看过答案，也不能靠新建会话或换一个 ID 洗成独立完成。

**延迟与迁移分别判断。**隔天重做原题可以提供某种延迟表现，但不自动是迁移；更换数值、题目编号也不自动证明新情境。

当前契约和 worker 已有部分题目、尝试与帮助关联字段，适合在原有机制上深化，而不是重新建设。

此外，系统记录的帮助“已送达”，并不能证明用户实际读过，也不能排除用户在其他软件或纸面获得帮助。产品表述应保留这个边界。study-assistant-opening-impleme…

## 七、具体开发路线：4 个里程碑、30 项任务

完整文件为每个任务写明了负责角色、依赖、现有入口、拟新增文件、测试、验收、回退和授权边界。下面给出实施主线。

### M0：目标与兼容边界——4 项任务

| 编号 | 任务 | 交付 |
|---|---|---|
| **V2-00** | 修订产品章程及冲突旧范围 | AI 主讲优先级、8 项目标和非目标写入同一份主计划 |
| **V2-01** | 处理当前真实 CI 失败 | 最小修复、真实检查结果，不绕过原质量规则 |
| **V2-02** | 准备一个真实教学单元 | 授权材料、教学目标、正确例题、典型错误、未曝光评测题 |
| **V2-03** | 确定活动、内容与证据兼容设计 | 无课程上下文、单一事实路径、版本存储、迁移和回退决定 |

M0 不应演变成长期重构。它解决的是后续必然会碰到的边界，同时准备可以直接用于前后端开发的真实样例。

## 九、怎样验收，才能知道没有偏离目标？

### 1. 工程正确性

必须覆盖的不只是成功路径，还包括：

无课程开始、跨用户拒绝、同一命令重试、异意图冲突、生成中刷新、取消后晚到结果、预算不足、结果未知、来源撤回、版本变化、双端草稿冲突，以及答案没有提前泄露到客户端。

**拒绝越权、保留未知、不发出超预算调用，也属于正确结果。**

测试仍按现有仓库规则执行：最近相关测试、所属包类型检查、隔离测试库、原有 CI；不因新增教学功能而重复建设整套门槛。

### 2. 教学内容质量

首单元需要有独立于模型输出的检查依据：

教学目标是否覆盖；关键前提有没有遗漏；引用是否真正支持结论；生成题是否可作答；答案和解析是否一致；图文是否使用相同参数；出现不确定内容时是否正确降级。

严重教学错误、虚假引用和答案泄露要单独报告，不能被整体平均评分掩盖。

### 3. 真实使用体验

应当观察用户是否能够直接开始、理解当前活动、自然求助、调整路径、保留产出并继续，而不只问“你觉得界面好不好看”。

建议先开展少量同意参与者的探索性试用。完整计划给出的 **5—8 人是发现体验问题的初始工程建议，不是证明学习效果的样本量**。

浏览器和真机验收继续按你已经约定的分工处理；未获得用户验收不能写成通过，但也不因此停止其他可推进的开发。

### 4. 学习效果

这里最容易出现一个隐蔽错误：

> 先筛选“独立且正确”的记录，再计算独立正确率。

这样会把错误答案从分母中移除。

建议先定义哪些观察具备测量条件，再在这些观察中计算正确与错误：

\[
\text{观察到的延迟独立正确率}
=
\frac{\text{合格观察中的正确次数}}
{\text{合格观察中的正确次数}+\text{错误次数}}
\]

同时报告缺失、受助、过早、版本失效、无法核验和实际参与情况。空分母表示未知，不是 0% 或 100%。旧实施指南已经将这一统计问题列为优先核查事项。study-assistant-opening-impleme…

还要进一步注意：不同策略可能改变用户求助或参与的概率，**只比较两组最终独立完成者，也不能直接得到因果结论**。正式研究应预先规定分配方式、主要结局、缺失处理与样本量；评测题与答案要与教学生成隔离。

没有对照、样本较小或只做模拟时，可以报告观察结果，不能包装成普遍提分。

## 十、如何控制范围、成本和回退风险？

### 不把性能优化变成提前更换架构

先测量从请求到首个**已检查、可学习的教学块**的时间，而不是用首个未校验 token 充当教学已就绪。

当前活动优先，后续有限预取；局部改写只改必要部分；生成修复次数和费用有上限；未知请求先核对，不盲目重试，也不自动换 provider。

具体时延和费用目标应在固定模型、材料和并发条件下测量后确定。完整计划中的初始性能门槛明确标为待确认工程建议，不是已有数据。

### 回退功能，不丢弃学习产出

新内容采取版本化保存，功能按用户和组件类型分批开放。回退时停止新生成或新策略，但用户已经产生的笔记、草稿、尝试和学习记录仍保留、可读取或导出。

从新持久化能力上线起就考虑备份与权限，不把数据恢复留到最后一刻。

### 不用“全部任务完成”代替实际交付

每个任务分别记录工程、真实模型、用户体验与学习效果状态。任务账本里的 `proposed` 不能因为文件存在而自动改成 `verified`。

旧验收材料可以复用，但只能证明其原本覆盖的范围；普通小改动不新增一堆形式化报告，发布时再按原位置汇总必要证据。这与仓库现有协作要求一致。

## 十一、本轮已经验证了什么，尚未验证什么？

**已经完成：**当前提交与关键源码核查、CI 状态和日志读取、相关论文及官方实现资料调研、旧实施指南对照，以及任务依赖与目标映射检查。

**尚未完成：**在项目完整环境中运行这些新功能、数据库事务与并发验证、真实 provider 集成、浏览器和真机体验，以及真实学习者效果研究。

容器克隆仓库因网络解析失败而未完成，因此本轮通过 GitHub 连接器进行源码核查。独立设计模型的通过不能替代仓库测试，更不能证明教学有效；当前 CI 失败也没有在这次研究任务中被修改或重跑。

## 最终实施决定

**第一批执行 V2-00 至 V2-03：收口目标、处理真实质量失败、准备一个可核查教学单元、明确活动与证据的兼容边界。随后直接推进 M1 的 AI 主讲闭环。**

不要先去扩展更多连接器、重做全部知识库、训练复杂掌握模型或建设多 Agent 虚拟课堂。

这份二次开发计划的核心验收标准是：

> **用户进入之后，AI 能够直接开始可信的教学；用户能够理解、思考和实践，获得适当帮助，自主改变路线，并在下一次自然继续。系统对“用户学到了什么”的每一个判断，都不越过实际证据的边界。**

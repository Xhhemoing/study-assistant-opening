# Resource-constrained development

This VM has 2 CPU cores and about 2 GiB RAM. Keep expensive validation serialized across projects.

- Do not run full test, lint, typecheck, and build chains in parallel.
- During implementation, run the smallest targeted test or typecheck only.
- Run the full validation chain once, at task completion, and let the package scripts use `scripts/run-heavy.sh`.
- Do not start a second full validation chain while one is running; wait for the shared lock.
- Keep the dev server running, but do not treat hot reload as a reason to launch a full build.

# Brainstorm and algorithm governance

- Preserve reusable research, product reasoning, algorithm comparisons, and failed experiments under `docs/brainstorm/`; register every note in `docs/brainstorm/INDEX.md` and follow its template and status model.
- Every research note must point to concrete user scenarios, domain objects, application/package boundaries, and intended plan/ADR/task targets. Separate verified facts, assumptions, and proposals.
- Treat brainstorm notes as non-authoritative candidates. Before implementation, promote approved product decisions to `docs/plans/` and hard-to-reverse architecture decisions to `docs/decisions/`; never let a brainstorm note silently override the PRD, an approved plan, an ADR, or the current task order.
- For every product or technical module, consult and maintain `docs/brainstorm/ALGORITHM_MAP.md`. Define the user outcome, invariants, versioned baseline, candidate improvement, evaluation data and metrics, upgrade threshold, observability, and fallback before selecting an algorithm, model, framework, or storage strategy.
- Prefer the simplest explainable approach that meets measured requirements. Adopt a more complex algorithm only after replay, benchmark, shadow, or controlled product evidence shows a material improvement under current data, latency, cost, privacy, portability, and resource constraints.
- Keep formal assets and immutable events as the source of truth. Derived search indexes, embeddings, graph projections, summaries, assessments, recommendations, and plans must be versioned, explainable, rebuildable, and rollback-capable.
- After implementation or production learning changes an assumption, write the measured result and failure mode back to the relevant brainstorm note, then mark it `validated`, `rejected`, or `superseded` as appropriate.
